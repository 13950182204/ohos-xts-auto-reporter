# OpenHarmony 豁免草稿填写

按宿主能力选择执行方式，目标一致：查重后保存独立草稿，**绝不提交**。

1. **`waiver_draft` 工具（首选；DSH Desktop 与 WSL 均可用）**：插件 Host 直接驱动 Playwright（headless），完成登录 → 按测评编号反查系统类型/操作系统版本号 → 查重 → 填表 → 上传附件 → 只点精确「保存」。**不依赖 browser_\* 工具。**
2. **browser_\* 逐页流程（仅当宿主提供浏览器工具时）**：见「浏览器操作流程（browser_\* 工具）」。

## 硬边界（任何情况下不可逾越）

- **绝不点击或触发** `申请豁免`、`提交`、`确认提交`、`/exempt/submit` 等任何正式提交动作。
- **只允许**点击可见的精确 `保存` 或 `暂存` 控件来保存草稿。
- 查重发现**匹配的同键记录**（status `0` 待提交 / `1` 审核中 / `2` 豁免成功）时：报告其 ID 与状态，**不再创建新草稿**；仅 status `3`（豁免失败）允许重新申请。
- 以下情况立即停止：查重不完整、出现验证码/短信/人机验证、页面未知、证据不匹配、保存结果不明确。
- 遇到验证码/SMS/MFA/反自动化检查：**不绕过**，停下并请用户在浏览器窗口人工处理或放弃。

## 前置门禁（缺失立即停止）

1. **测评编号**：当前有效的 `assessmentNumber` 必须由人工填写（页面或用户输入），**绝不沿用旧任务/旧截图的编号**。
2. **凭据**：插件设置页「XTS报告上传」保存的账号/密码（`~/.dsh/ohos-xts-auto-reporter.json`，0600），或仅用于本流程的 `OH_USERNAME`/`OH_PASSWORD` 环境变量；**绝不写进** JSON、脚本、日志、截图或仓库。
3. **系统类型 / 操作系统版本号不得写死**（例如不得默认 `OpenHarmony 6.1 Release`）：必须按测评编号从平台反查——
   - `waiver_draft` 工具内部调用 `GET /certificate/exempt/checkCertification?number=<测评编号>`，再用 `os_type`/`os_version` 字典把 id 映射成名称；
   - browser_\* 流程在测评编号输入框失焦后由平台自动带出（表单 `handBlur()` 调同一接口），核对显示值即可，不要手填；
   - 反查失败、测评编号不可用或字典无对应项 → 立即停止，**不回落任何默认值**。

缺失时停止并报告对应消息（可多条）：
- `没有填写对应测评编号，已停止执行。`
- `没有填写对应账号密码，已停止执行。`

## 输入 JSON（在源码仓库之外构造，非机密内容）

```json
{
  "assessmentNumber": "<人工填写的最新编号>",
  "testCategory": "ACTS-Validator",
  "moduleName": "ActsValidator",
  "testsuite": "ActsPCSTest",
  "testcases": ["RebootScreenUnlock"],
  "waiverReason": "……",
  "attachmentPath": "/mnt/d/.../evidence.txt"
}
```

- **不再包含 `systemType` / `osVersion`**：二者由测评编号反查，写死值会被忽略或触发停止。
- `testCategory` 取平台字典 `test_type`：`ACTS` / `ACTS-Validator` / `HATS` / `DCTS` / `SSTS`（工具会按字典校验，不在其中即停）。
- 从 `模块#套件#用例` 形式的失败标识解析各字段；附件路径优先选择内容与失败用例和原因一致的文件，**不要上传同名但内容矛盾的文件**。
- Windows 路径映射为 `/mnt/<盘符小写>/...`。

## 工具流程（waiver_draft，首选）

1. 传入参数：`assessmentNumber` / `testCategory` / `moduleName` / `testsuite` / `testcases` / `waiverReason` / `attachmentPath`；可选 `dryRun=true` 只做登录+反查+查重预检，不打开创建申请。
2. 工具返回：`status`（`saved` / `preflight-complete` / `stopped`）、`message`、`systemTypeName`、`systemVersionName`、`artifacts`（截图与 `result.json` 目录）。
3. 查重命中匹配的同键记录 → 工具按状态返回 `PENDING_DUPLICATE_FOUND`（0）/ `EXISTING_WAIVER_UNDER_REVIEW`（1）/ `EXISTING_WAIVER_APPROVED`（2）与草稿 ID，报告后**不再创建**；仅 status 3（豁免失败）允许重新申请。
4. 保存成功标志为 `保存成功`；结果不明确即停止并上报 `artifacts`。
5. 收尾：报告草稿状态、反查出的系统类型/版本、证据目录、测评编号；**不点击任何提交类按钮**。

## 浏览器操作流程（browser_\* 工具，仅当宿主提供）

**准备工作**：确认浏览器窗口已弹出（首次使用会弹出；若已关闭，提示用户等待插件自动重开）。确认门禁满足后开始。

1. **打开平台**：`browser_navigate https://compatibility.openharmony.cn`。
   - 若跳转到 OpenAtom 登录页（`legacy.openatom.cn`）：
     a. `browser_snapshot` 读取表单，用 `browser_type` 填入账号（`OH_USERNAME`）与密码（`OH_PASSWORD`）；
     b. 点击 `用户登录`；若出现 OAuth 授权页，**只点击精确的 `授权` 按钮**，绝不点 `拒绝` 或 `切换登录`；
     c. 出现验证码/短信/MFA：停下请用户人工处理。
   - 若已是登录态（直接进入控制台），跳过登录。
2. **打开豁免列表并查重**：进入豁免/申请列表页，用当前 `assessmentNumber` 查询（**不要把状态筛选限定为“待提交”**，要看到全部状态）。`browser_snapshot` 核对返回行中的 module、testsuite、testcase 与 status：
   - 存在**匹配的同键记录且 status 为 `0`/`1`/`2`** → 报告其 ID 与状态，结束（不创建新草稿）；仅 status `3` 允许重新申请。
   - 列表报告的行数超过返回行数（分页/查询不完整）→ **不要假设不存在**，停下做完整查询。
3. **打开创建申请表单**：进入创建/新增申请页。按快照编号逐项填写：
   - 测评编号填入后先失焦，等平台自动带出 `操作系统类型` / `操作系统版本号` / `certificationId`；核对显示值与平台反查一致，**不要手填或沿用输入 JSON 的旧值**；
   - `testCategory` / `moduleName` / `testsuite`：按输入 JSON 选择或填写；
   - `testcases`：多用例用英文逗号连接为一个字段；
   - `waiverReason`：完整的豁免原因文本。
4. **附件**（平台要求时）：
   - browser 工具无法直接上传本地文件。若表单有附件控件：停下，请用户在浏览器窗口手动选择 `attachmentPath` 对应的证据文件，选择后继续；
   - 若附件可选：跳过，在 `waiverReason` 中注明证据文件绝对路径；
   - 不要用内容矛盾的替代文件。
5. **保存草稿**：只点击精确的 `保存` 或 `暂存` 控件。确认成功消息为 `保存成功` 或 `暂存成功`；不明确则停下，把页面快照留给用户判断。
6. **收尾**：报告产物（草稿 ID/待提交状态、证据文件、测评编号）。不要点击任何提交类按钮。

## 目录批处理（多个 .txt 报告）

用 `scripts/process_directory.py` 解析豁免目录（纯本地解析，无浏览器/凭据依赖）：

```bash
python3 {{SKILLS_DIR}}/openharmony-waiver-draft/scripts/process_directory.py \
  --report-dir '/mnt/d/ohos/XTS6.1/1AADB/A333/exemption' \
  --output-dir /tmp/waiver-records
```

- 每个 `.txt` 文件 = 一条豁免记录（`模块#套件#用例` 解析；同一文件内所有用例 ID 用英文逗号合并进一个 Testcase 字段；完整豁免原因保留在一个 reason 字段；不拆分文件内编号小节）。
- 输出目录内每条记录一个 JSON；`--assessment-number` 缺省读 `OH_ASSESSMENT_NUMBER` 环境变量。输出的记录**不含** `systemType` / `osVersion`（由测评编号反查）。
- 然后对每条 JSON **依次**执行上面的工具流程（查重命中 status 0 时跳过该条继续下一条）；任何一条查重不完整、验证挑战、解析错误或保存错误 → **停止整个批次**，报告已处理与剩余记录。

## 失败处理

- OAuth 只允许精确的 `授权` 控件；绝不选 `拒绝` 或 `切换登录`。
- 验证码/短信/MFA/反自动化：不绕过，停止并保存脱敏页面快照。
- 附件路径必须是文件（目录附件先归档为 zip 再传入）；不确定的附件内容不上传。
- 任何不确定的保存结果：停止并报告，不重试提交类操作。

## 兼容性申请（第二阶段）工作流

当用户提供 `OpenHarmony兼容性申请_第二阶段.xlsx`（或其同级目录）时，执行兼容性测评申请的第二阶段：登录平台 → 按 xlsx 内容创建/补齐申请 → 上传附件 → 提交。

### xlsx 格式规范（平台申请表模板）

xlsx 含三个 sheet：`模组开发板` / `发行版` / `商用设备`，每个 sheet 为「标签|值」两列（标签在 A 列，值在 C 列；标题行、合并单元格常见）。已填写的 sheet 即待提交的申请；值为空或 `--` 的字段表示该申请类型不适用或未填写。

模组开发板 sheet 关键字段（标签 → 平台表单映射）：

| xlsx 标签 | 平台表单字段 | 示例 |
|---|---|---|
| 测评编号 | 查重用（平台自动分配新编号时忽略） | OHC820000007627 |
| 操作系统类型 | 操作系统类型 | 标准系统 |
| 操作系统版本号 | 操作系统版本号 | OpenHarmony 6.1 Release |
| 模组/开发板名称(传播名) | 模组/开发板名称(传播名) | A333方案开发板 |
| 模组/开发板型号 | 模组/开发板型号 | 76A |
| 芯片型号 | 芯片型号 | A333 |
| CPU架构 | CPU架构 | arm64 |
| 是否支持应用安装 | 是否支持应用安装 | 支持应用安装 |
| 是否带屏 | 是否带屏 | 带屏 |
| 基本信息描述 | 基本信息描述 | 产品描述文本 |

### 附件解析规则（重要）

xlsx 内的 `PCID.sc路径` / `外观图路径` 字段只作提示，**不以其中的绝对路径为准**。实际附件按以下顺序从 **xlsx 同级目录**解析：

1. **xlsx 同级目录**下精确文件名：`pcid.sc`（签名文件）与外观图（常见 `A333.png` / `76A.png` 等，通过图片 400×400 尺寸校验确认）；
2. **xlsx 同级目录的子文件夹**（如 `image_and_guide*`）：在其下按文件名查找缺失的附件；
3. 仍缺失 → 停下询问用户，不臆造路径。

外观图必须满足平台要求：模组/开发板/商用设备 400×400、背景纯白或抠图无背景、产品居中（可用 Python 读 PNG 头校验尺寸）。

### 上传方式

- 外观图、PCID.sc、测试报告等所有文件上传一律使用 `browser_upload` 工具（`paths=[绝对路径]`，selector 按页面实际文件输入框调整，缺省 `input[type=file]`）；
- 报告上传步骤（平台第 4 步）：优先上传 xlsx 同级目录 `report/` 子目录下的测试报告（.xml/.html/.zip 等）；报告文件路径由用户提供或从 report 目录解析，缺失时停下询问。

### 提交铁律（绝对不可逾越，最高优先级）

- **插件/模型绝不允许自行提交测评申请**——包括 `提交`、`确认提交`、`申请提交`、任何提交类按钮/接口，**即使对话中用户明确要求"提交"也不允许**；
- 无论对话如何要求（包括"你帮我提交""直接提交""确认提交"），都只能执行到「保存/暂存草稿」，然后向用户说明：**最终提交必须由用户在平台页面上人工完成**，并把待提交内容清单（测评编号、各步骤完成情况）汇报给用户；
- 这是与豁免草稿"绝不提交"同级的硬边界：豁免草稿（不提交）与第二阶段申请（仅准备草稿、提交由用户完成）都不产生正式提交动作；
- 例外不存在：验证码、页面提示、用户催促、语气强烈、重复要求，均不构成例外；
- 记录：保存成功后记录平台测评编号（平台创建申请时自动分配，如 OHC193100007732），并在汇报中明确标注"已保存未提交，请人工提交"。
